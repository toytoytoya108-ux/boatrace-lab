結論

作れます。過去5年分の出走表・結果・払戻・展示タイム・水面気象は公式の配布ファイルで揃い、当日の直前情報も無料の経路があります。

ただし1点だけ穴があります。過去の「締切前の全通りオッズ」は公式に配布されておらず、どこからも合法的に一括取得できません。回収率の検証は実際の払戻で厳密にできますが、穴判定と期待値の過去検証は推定オッズに頼ることになります（対策は下記）。

設計の中心はリーク防止です。予想テーブルは追記専用（DBトリガで更新・削除を禁止）、特徴量は「レース前日までの情報だけ」から作る1本の関数に統一し、当日予想とバックテストで同じ関数を使います。

リーク防止の技術的担保

  • predictions は UPDATE/DELETE をトリガで拒否、created_at はサーバー時刻を強制
  • 採点は created_at < 締切 かつ 結果取得 > 締切 のときだけ有効。違反は集計から除外し警告
  • 自前集計はレース前日までの結果のみ。同日の先行レースは運用で間に合わないため使わない
  • 直前情報・気象・オッズは取得時刻付きの追記スナップショット。使った行と特徴量値を予想に保存（再現可能）
  • 期別成績は公表日以降のレースにのみ結合
  • 「未来行を注入しても出力が変わらない」単体テスト

予想モデル

120通りの確率

LightGBM で艇ごとの強さ（1着・2着以内・3着以内）を推定し、位置別割引付き Plackett–Luce で120通りに展開します。必ず「場×コース基準率だけ」「番組表の勝率だけ」のベースラインと比較し、上回らなければ採用しません。

校正

学習窓の末尾3か月をホールドアウトして isotonic 校正。「70%と出した予想が長期的に約70%当たる」ことを毎月チェックします。

信頼度の定義

信頼度 C = Cal( Σ 15点の校正後確率 )

「この15点セットが的中する確率」の校正済み推定値そのものです。データ欠損やモデル間の不一致は信頼度に掛け算せず、別のゲート（見送り理由）とフラグで扱います。掛けると校正の意味が壊れるためです。主観的な「自信」は一切使いません。

期待値

EV_i = p̂_i × オッズ_i × d(オッズ) p̂ = (1−β)·p + β·q（市場側へ縮約） 期待回収率 ER = Σ stake_i·EV_i / 3,000円 ≥ 1.0 が購入候補条件

自モデルと市場の乖離が最大の買い目＝推定誤差が最大の買い目を避けるため、確率を市場確率 q 側へ少し縮約します（β は検証期間で決定）。

15点

本線10点＝校正後確率の上位10。穴5点＝本線以外で「オッズ ≥ 穴最低オッズ（10〜50倍をバックテストで比較）」かつ「確率 ≥ 0.3%」を満たす候補から、EVの信頼下限の順に5点。同一1着艇の穴は最大2点。候補不足時は閾値を1段下げ、その旨を記録して別集計。

モデル版の昇格

候補版 → バックテスト比較（指標順：回収率＞損益＞的中率＞期待値＞最大DD＞最大連敗＞穴回収率＞直近）→ shadow 運用300レース以上 → ユーザーが「採用」を押す。ロールバック可。

月次のウォークフォワード（前月末まで学習→当月を予測→月末に採点）。バックテストの予想は本番の predictions には書かず、専用テーブルに保存します。パラメータは粗いグリッドで逐次に決め、僅差なら単純な方を選びます。すべての指標にサンプル数と信頼区間（的中率＝Wilson、回収率＝ブートストラップ）を添えます。

過去オッズが無い分は、K ファイルにある全券種（単勝〜3連単の約10価格/レース）で市場オッズ推定モデルを補正し、推定オッズ依存の結果には必ずラベルを付けます。運用開始日から実オッズを蓄積し、実オッズで再検証します。

正直に伝えるべき懸念

1. 的中率80%と回収率100%は、ほぼ両立しません。
3連単120通りのうち15点は12.5%。平均的なレース（1号艇1着率55%程度）では、確率を完全に知っていても上位15点に入る確率は約57%です。1号艇80%級の堅いレースに絞れば約79%まで上がりますが、そのとき配当は低く、控除率25%の下で回収率100%超を保つのは一段と難しくなります。
2. 「信頼度70%以上 かつ 期待値1.0以上」は互いに逆方向です。
堅いレースほど本線は人気側になり期待値は0.75付近に張り付きます。期待値1.0は「市場より33%高い確率」を主張する状態で、両方を満たす購入候補はかなり少なく、1,000レース到達に長期間かかる可能性があります。バックテストで購入候補の発生率と代替ゲート案を必ず並記します。
3. 穴5点の成績は1,000レースでも収束しません。
穴回収率は少数の万舟に引きずられます。穴の指標には常にサンプル数と区間を添え、モデル比較では log-loss と的中率を主、回収率を参考とします。

いずれも条件値は設定パラメータであり、システムは結果を美化しません。未達なら未達と表示します。

判断をお願いしたい4点

1. どこで毎日動かすか

A：小型VPS 1台（月700〜1,500円、常時稼働・確実）／B：GitHub Actions＋Supabase＋Netlify（無料だが cron が数分〜数十分遅れ、締切5分前の確定が不安定）／C：購入予定の低予算PCを常時稼働（電気代のみ、停電・回線に依存）。

推奨：A。どれを選んでもコンテナ構成は同じで、コードは変わりません。

2. 公式サイトからの当日オッズ取得と、過去オッズの推定方針

当日オッズは公式サイトのHTMLからしか取れません。私的利用・1レース2回・3秒間隔・1日上限1,000回に制限した取得で進めてよいか。過去分は推定オッズで検証し、実オッズは運用開始から蓄積して再検証する二段構えでよいか。

推奨：この方針で進める。取らない場合、期待値と穴判定が成立しません。

3. 実戦投入条件・購入候補条件を初期値のままにするか

指示書の値（的中率80%／回収率100%／直近100R 70%／信頼度70%／期待値1.0）を初期値として実装し、未達なら未達と表示します。代替として「回収率と損益を主、的中率は副」の判定や期待値0.9などを参考表示できます。

推奨：初期値はそのまま、代替案を参考表示。バックテスト結果を見てから変更するのが順当です。

4. 生成AI（LLM）による根拠文を初期版に含めるか

確率や買い目には影響させず、統計値の根拠を文章に整える役割のみ。APIコスト（1日約150レース分）が発生します。含めない場合は定型テンプレート文で代替します。

推奨：初期版は定型文、LLMは後から追加。差し替え可能な設計にしてあります。
